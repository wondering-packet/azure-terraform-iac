## T1 — What Terraform Is and Isn't

### The core idea

Terraform is a **declarative** infrastructure tool. You describe the desired end state — what resources should exist, with what configuration — and Terraform figures out how to get there. You don't write procedural steps ("first create this, then attach that"). You write a description of reality as it should be. The execution engine is Terraform's planner, not you.

### What Terraform is

- An **infrastructure provisioning tool** — creates, updates, destroys cloud resources
- **Cloud-agnostic** — same workflow for Azure, AWS, GCP, or any provider with an API
- **Idempotent** — running `apply` twice with the same config produces no change the second time
- **State-aware** — tracks what it deployed so it can diff against desired state on every run

### What Terraform is not

- Not a configuration management tool — it provisions infrastructure, it doesn't configure software inside VMs (that's Ansible)
- Not a scripting language — HCL has no traditional loops, no user-defined functions, no imperative flow control
- Not real-time — Terraform runs on demand, it's not a daemon watching for drift

### Terraform vs alternatives

| Tool | Model | Azure native? |
|---|---|---|
| Terraform | Declarative, cloud-agnostic | Via azurerm provider |
| Bicep | Declarative, Azure-only | Yes |
| ARM Templates | Declarative, Azure-only, verbose JSON | Yes |
| Pulumi | Imperative/declarative, real code (Python/TS) | Via SDK |
| Azure CLI scripts | Imperative | Yes |

> Terraform wins for multi-cloud portability and ecosystem maturity. Bicep is a strong Azure-only alternative. The concepts here — state, providers, modules, remote backends — translate to every other IaC tool.

## T2 — Providers, Resources, Lifecycle

### Providers

A provider is a plugin that translates HCL into API calls for a specific platform. For Azure: `hashicorp/azurerm`. Downloaded by `terraform init` into `.terraform/`.

```hcl
terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 3.100"
    }
  }
}

provider "azurerm" {
  features {}
}
```

`features {}` is required by azurerm even when empty. `~> 3.100` is the **pessimistic constraint operator** — allows `3.100.x` patches but locks the minor version. `~> 3.0` allows any `3.x`; `= 3.100.0` pins exactly. Use `~>` to allow security patches without accidental major upgrades.

### The `.terraform.lock.hcl` file

After `terraform init`, a `.terraform.lock.hcl` file records the exact provider version and checksums selected.

| File | Commit to Git? | Why |
|---|---|---|
| `.terraform.lock.hcl` | ✅ Yes | Locks provider versions — team gets identical behavior |
| `.terraform/` directory | ❌ No | Binary provider downloads — large, OS-specific, regenerated by init |
| `terraform.tfstate` | ❌ Never | Contains secrets and resource IDs — use remote state |
| `*.tfvars` | ❌ Usually no | May contain secrets |

> Common mistake: gitignoring `.terraform.lock.hcl` while committing `.terraform/`. It's the reverse — lock file goes in, directory stays out.

### Resource lifecycle meta-arguments

The `lifecycle` block, `depends_on`, and provider aliasing are **introduced** here as concepts but drilled with exercises in Day 1 (Topic 6). Briefly:

- `lifecycle { prevent_destroy / create_before_destroy / ignore_changes }` — control create/update/destroy behavior
- `depends_on` — explicit ordering when Terraform can't infer it from references
- `provider = azurerm.alias` — point a resource at a non-default provider (multi-subscription)

## T3 — Terraform State

### What state is

A JSON file (`terraform.tfstate`) mapping HCL resource definitions to real cloud resource IDs. It's Terraform's memory — the source of truth for what Terraform thinks it owns.

### How plan uses state

```
HCL (desired state)
      ↓  diff
State file (last known state)  →  identifies which cloud resources to query
      ↓  reconcile with live cloud config
Plan output (delta to reach desired state)
```

Terraform queries the live cloud on every plan/apply — but only for resources it knows about via state. State scopes the query; it doesn't replace it.

### State file anatomy

```json
{
  "version": 4,
  "terraform_version": "1.7.0",
  "resources": [
    {
      "mode": "managed",
      "type": "azurerm_resource_group",
      "name": "main",
      "instances": [{
        "attributes": {
          "id": "/subscriptions/.../resourceGroups/rg-vg-lab-wus-01",
          "location": "westus",
          "name": "rg-vg-lab-wus-01"
        }
      }]
    }
  ]
}
```

The binding: `type` + `name` in state matches `resource "azurerm_resource_group" "main"` in HCL. The `id` is what Terraform uses to query live config for drift.

### What happens if state is lost

Terraform has no memory. `apply` tries to create everything again — the cloud errors with "already exists" or creates duplicates. Infrastructure becomes orphaned — running, billing, unmanaged. Recovery: `terraform import` pulls existing resources back into state (drilled in a later day).

### Drift detection

If someone edits a resource in the portal, `terraform plan` shows the delta:

```
~ address_space = ["172.22.16.0/20"] -> ["172.22.0.0/16"]
```

No rollback — you fix forward by updating HCL to match desired reality, then apply.

### Remote state

Local state works for solo learning. Teams use remote state — a shared backend with locking. **This is drilled fully in Day 2** (backends, locking, workspaces). The concept:

```hcl
terraform {
  backend "azurerm" {
    resource_group_name  = "rg-vg-lab-wus-01"
    storage_account_name = "stvglabwustfstate"
    container_name       = "tfstate"
    key                  = "networking/hub-spoke"
  }
}
```

### .gitignore — non-negotiable

```gitignore
.terraform/
terraform.tfstate
terraform.tfstate.backup
*.tfvars
crash.log
```

`.terraform.lock.hcl` is the exception — it goes in Git.

## T4 — HCL Syntax: Blocks, Arguments, References

### Block types

| Block | Labels | Purpose |
|---|---|---|
| `terraform` | none | Settings, required_providers, backend |
| `provider` | provider name | Provider config |
| `resource` | type + local name | A managed infrastructure object |
| `variable` | variable name | Input parameter (drilled Day 1) |
| `output` | output name | Exposed value (drilled Day 1) |
| `locals` | none | Computed values (drilled Day 1) |
| `data` | type + local name | Read existing infra (drilled Day 1) |
| `module` | module name | Call a reusable module (drilled Day 8) |

### Resource block anatomy

```hcl
resource "<provider_type>" "<local_name>" {
  argument = "value"              # string
  argument = ["a", "b"]           # list
  argument = { key = "val" }      # map
  argument = var.myvar            # variable reference
  argument = local.computed_val   # local reference

  nested_block {
    argument = value
  }
}
```

Resource type names (`azurerm_virtual_network`) are fixed by the provider. The local name is yours, scoped to the module. Reference: `registry.terraform.io/providers/hashicorp/azurerm/latest/docs`.

### References between resources

Syntax: `<resource_type>.<local_name>.<attribute>`

```hcl
resource "azurerm_resource_group" "main" {
  name     = "rg-vg-lab-wus-01"
  location = "westus"
}

resource "azurerm_virtual_network" "hub" {
  name                = "vnet-vg-lab-wus-hub"
  address_space       = ["172.22.0.0/20"]
  location            = azurerm_resource_group.main.location   # reference
  resource_group_name = azurerm_resource_group.main.name       # reference
}
```

References create **implicit dependencies** — Terraform creates the RG before the VNet automatically. Always prefer references over hardcoded strings.

### Project file structure convention

```
project/
├── .gitignore
├── .terraform.lock.hcl    ← commit this
├── main.tf                ← terraform{} + provider{} blocks
├── variables.tf           ← variable declarations
├── outputs.tf             ← output declarations
├── locals.tf              ← computed locals
├── terraform.tfvars       ← variable values (don't commit if secrets)
└── versions.tf            ← optional: pin terraform + provider versions
```

Splitting by purpose is convention, not requirement — Terraform merges all `.tf` files in a directory.

## T5 — The Type System at a Glance

Full depth (validation, `optional()`, `can()`) is in Day 1. The essentials:

### Primitive types

| Type | Example |
|---|---|
| `string` | `"westus"` |
| `number` | `42` |
| `bool` | `true` |

### Collection types

| Type | Example | Notes |
|---|---|---|
| `list(T)` | `["a", "b"]` | Ordered, indexed, duplicates allowed |
| `set(T)` | — | Unordered, no duplicates — used with `for_each` |
| `map(T)` | `{ key = "val" }` | Key-value, all values same type |
| `object({...})` | `{ name = "x", cidr = "10.0.0.0/8" }` | Named attributes, mixed types |

### The distinction that matters most

```hcl
# map(string) — all values the same type
map(string)   →  { web = "172.22.10.0/24", app = "172.22.11.0/24" }

# object({...}) — one structured value, named fields, mixed types
object({ cidr = string, has_nsg = bool })

# map(object(...)) — N structured values, each keyed
map(object({ cidr = string, has_nsg = bool }))
→ { web = { cidr = "...", has_nsg = true }, app = { cidr = "...", has_nsg = true } }
```

Rule of thumb carried through the whole program: **singular resource → `object({...})`; variable number of the same shape → `map(object({...}))`.** A hub VNet (always one) is an `object`; spoke VNets (many) are a `map(object)`.

## T6 — variables.tf and terraform.tfvars: the matching contract

This is the single most important mechanical detail to get right early.

`variables.tf` **declares** a variable — its name, type, constraints. `terraform.tfvars` **provides the value**. The link between them is the **variable name** — it must match exactly.

```hcl
# variables.tf — DECLARES a variable named "subnets"
variable "subnets" {
  type = map(object({
    cidr    = string
    has_nsg = bool
  }))
}
```

```hcl
# terraform.tfvars — PROVIDES a value for the SAME name "subnets"
subnets = {
  web = { cidr = "172.22.10.0/24", has_nsg = true }
  app = { cidr = "172.22.11.0/24", has_nsg = true }
}
```

> **The name on the left in `terraform.tfvars` must exactly match the name in the `variable` block.** If `variables.tf` declares `subnets` but `terraform.tfvars` assigns `subnet = {...}` (missing the s), Terraform does two bad things: it ignores your `subnet` assignment as an undeclared variable warning, and it prompts for (or errors on) the unset `subnets` variable. There's no fuzzy matching — the strings are compared literally. This is the number-one source of "why isn't my value being picked up" confusion.

The same matching applies to every source of variable values:

| Source | How the name is expressed |
|---|---|
| `terraform.tfvars` | `subnets = {...}` |
| `-var` CLI flag | `-var="subnets={...}"` |
| Environment variable | `$env:TF_VAR_subnets = "{...}"` (prefix `TF_VAR_` + exact name) |

### Contrast: what each file is for

| | `variables.tf` | `terraform.tfvars` |
|---|---|---|
| Role | Declares the variable exists — name, type, validation, default | Supplies the actual value |
| Contains | `variable "x" { type = ... }` blocks | `x = <value>` assignments |
| Committed to Git? | Always | Not if it holds secrets |
| Required? | Yes | No — defaults cover it if omitted |
| Analogy | Function signature | The arguments you call it with |

If a variable has no default and no value is supplied anywhere, Terraform prompts interactively at plan/apply — which hangs CI/CD pipelines. Always supply values in tfvars or env vars for automation.

### Variable value precedence (lowest → highest)

```
default in variables.tf
  → terraform.tfvars
    → *.auto.tfvars
      → TF_VAR_<name> env var
        → -var CLI flag   ← wins everything
```

## The Terraform Workflow

| Command | Does | Writes state? |
|---|---|---|
| `terraform init` | Downloads providers, sets up backend. Run once per project or after provider/backend changes. | No |
| `terraform fmt` | Formats `.tf` files to standard style. | No |
| `terraform validate` | Checks HCL syntax offline — no API calls. | No |
| `terraform plan` | Diffs HCL vs state vs live cloud. Dry run. | No |
| `terraform apply` | Executes the plan. Prompts unless `-auto-approve`. | Yes |
| `terraform destroy` | Deletes all managed resources. | Yes (empties it) |

```
Write HCL → init → plan → apply → (change HCL) → plan → apply → ... → destroy
```

### Plan output symbols

| Symbol | Meaning | Risk |
|---|---|---|
| `+ create` | New resource | Low |
| `~ update in-place` | Attribute change, resource stays | Low — review |
| `- destroy` | Resource deleted | High — verify |
| `-/+ replace` | Immutable attribute changed, must recreate | Critical — check dependents |
| `<= read` | Data source re-read | Informational |

> `-/+` on a foundational resource (VNet, subnet) is like a BGP session drop on a core router — everything inside may be affected. Always read the full plan before typing `yes`.

### Authentication (PowerShell / Service Principal)

The azurerm provider reads credentials from environment variables. Set them before running Terraform:

```powershell
$env:ARM_CLIENT_ID       = "<client-id>"
$env:ARM_CLIENT_SECRET   = "<client-secret>"
$env:ARM_TENANT_ID       = "<tenant-id>"
$env:ARM_SUBSCRIPTION_ID = "<subscription-id>"
```

Never hardcode credentials in `.tf` files. Never commit them.
